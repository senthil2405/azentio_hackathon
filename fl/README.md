# Federated model-learning track (P2): synthetic demonstration

A separate, **opt-in** programme (spec §11). It is not the collective-learning hub: no portal observation is used for training, and portal membership or publishing consent does not imply training consent.

## Run it
```bash
npm run fl:provision          # create 3 isolated synthetic client datasets (fl/clients/<id>/data.json)
npm run fl:round -- normal 5  # 5 federated rounds → candidate model in fl/registry/models/
npm run fl:round -- dropout 5 # Eastgate fails from round 2
npm run fl:round -- poison 5  # Meridian sends a malicious update
node fl/src/registry.ts approve normal-r5 <reviewer> "<reason>"   # explicit human deployment decision
node fl/src/registry.ts rollback <reviewer> "<reason>"
```
The coordinator ledger is `fl/registry/ledger.jsonl` (append-only).

## Learning task, model and schema
- **Task:** predict whether a synthetic SME loan becomes 60+ days past due within 12 months.
- **Model:** logistic regression with 5 weights and a bias. Each participant trains locally with SGD (5 epochs per round).
- **Feature schema `sme-default-v1`:** standardised `revenue_change_vs_same_season`, `revenue_change_vs_prev_quarter`, `debt_service_coverage`, `seasonality_index`, `years_trading`.
- **Compatibility:** an update must carry `schemaVersion = sme-default-v1`, the current base model version, a 6-element finite vector and a positive sample count. Anything else is rejected.
- **Data:** generated by `fl/src/data.ts`. True risk depends on the *seasonality-aware* change, while the naive quarter-on-quarter change is polluted by seasonal dips. This mirrors the portal's illustrative scenario.

## Isolation
Each participant runs as **its own process** (`fl/src/client.ts`) with access only to its own data file. It receives the global model on stdin and returns only a parameter delta and a sample count. The coordinator (`fl/src/coordinator.ts`) never opens participant data files. The ledger records participant IDs, sample counts, norms, rejection reasons and metrics, never training examples. A check over the ledger finds 0 feature vectors.

## Results (5 rounds, synthetic holdout of 1,500 from a separate seed)
| Model | Accuracy | Log loss | Recall | Precision |
|---|---|---|---|---|
| Majority-class baseline | 0.741 | — | 0 | — |
| Northbank local-only | 0.764 | 0.494 | 0.442 | 0.557 |
| Meridian local-only | 0.773 | 0.517 | 0.165 | 0.810 |
| Eastgate local-only | 0.771 | 0.491 | 0.550 | 0.559 |
| **Federated (normal)** | **0.785** | **0.477** | 0.314 | 0.689 |
| Federated (dropout: Eastgate fails from round 2) | 0.785 | 0.479 | 0.291 | 0.711 |
| Federated (poison: Meridian's update rejected every round) | 0.774 | 0.492 | 0.337 | 0.618 |

**Participation and weighting:** FedAvg weighted by sample count (900 / 600 / 300), with each participant's weight capped at 0.6. The minimum is 2 valid participants per round; below that the round is aborted and the model is left unchanged.

**What the results do and don't show:** federation improves log loss and accuracy over every single-client model on this synthetic task. The recall/precision trade-off differs, though, so a real programme would choose a decision threshold with business owners. Three clients and one synthetic holdout are far too small to claim generalisation.

## Effect of skewed client distributions
The clients deliberately differ:
- Northbank is agri-seasonal (seasonality 0.8).
- Meridian is retail (seasonality 0.35, lower default rate).
- Eastgate is tourism (seasonality 0.9, higher default rate, fewest samples).

Sample weighting means the largest client (Northbank) pulls the global model towards its distribution. The 0.6 cap limits this, but the model still under-represents Eastgate's high-risk, small portfolio. You can see it in recall: Eastgate's local model recalls 0.55 of defaults, the federated model 0.31. When Eastgate drops out, the global model drifts further towards the lower-risk clients (recall falls to 0.29). Mitigations to evaluate include per-client evaluation before any deployment, fairness-aware weighting, and a minimum share per participant. None are implemented here.

## Threat model (summary)
| Threat | Status in this demo |
|---|---|
| **Update leakage:** gradients or deltas can reveal information about training data | **Not mitigated cryptographically.** Updates are bounded (L2 clip at 1.0) and only aggregates are logged. No secure aggregation and no differential privacy are implemented, so **no formal privacy guarantee is claimed.** |
| **Poisoning:** a malicious client sends a crafted update | **Partially mitigated:** schema, version and finiteness checks; norm clipping; rejection of updates with norm > 5.0 (demonstrated). This does not detect subtle, small-norm poisoning. Robust aggregation (median, trimmed mean) is future work. |
| **Free-riding / impersonation** | **Simulated:** participants are identified by a registry ID. Production needs authenticated participants (mTLS or signed updates). |
| **Small cohort** | **Implemented:** at least 2 valid participants per round. The production threshold needs approval. |
| **Model inversion of the deployed model** | Out of scope. Access to the deployed model should itself be restricted and audited. |

**Honest labels:**
- **Implemented:** local training, isolation by process, update validation, clipping, outlier rejection, minimum cohort, weighted FedAvg, holdout evaluation versus baselines, consent registry, ledger, candidate registration, human approval, rollback.
- **Simulated:** participant authentication, network transport.
- **Not implemented:** secure aggregation, differential privacy and DP accounting, robust aggregation.

Local data retention alone does **not** provide confidentiality, anonymity or regulatory compliance.

## Consent, withdrawal and lineage
- **Consent:** `fl/programme/consents.json` holds programme-specific training consent per participant. It is separate from the portal's `training` consent flag, which no current programme uses.
- **Withdrawal:** setting `withdrawnAt` excludes the participant from all **future** rounds, and the exclusion is recorded in the ledger. Models already aggregated with their updates are **not** "untrained". The policy is that every candidate records its participants and rounds in `lineage`, and a reviewer can decline to approve, or roll back, any model whose lineage includes a withdrawn participant. Retraining without them is a separate, explicit decision.
- **Lineage:** each model record stores its version, base schema, participants, rounds, aggregation policy, evaluation and the reviewer's decision. The ledger is append-only.
- **Deployment and rollback:** new models are `candidate` only. `registry.ts approve` (named reviewer and reason) is the only way to deploy. `rollback` restores the previously deployed version and logs who did it and why.
